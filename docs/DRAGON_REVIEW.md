## 2. 引言与工作定位：真正解决的问题

**依据：§1-2，PDF p.1-3（2809-2811）。**

DRAGON 的动机是：LLM 直接输出 COP 解时，随着节点数与序列长度增长，逻辑连贯性、组合约束遵守和上下文容量都成为瓶颈。它提出两个研究问题：LLM 能否在不直接求解全局问题的情况下识别潜在改进区域，以及能否带着新增边界约束求解小问题。

方法把大规模问题转换为反复的分解与重建任务。其贡献不只是一个提示词，而是 **两类 agent、状态传递、静态区域压缩、局部约束整合、可行性检查、失败经验再提示和搜索接受机制共同构成的求解系统**。其 agent 通信主要通过问题与解状态传递，不能仅凭多代理名称将它理解为多个独立策略主体博弈。

作者把自己的路线与代码合成、端到端训练和自然语言数学建模区分开：DRAGON 的主体是在每个待解实例上由 LLM 直接提出分解和局部候选解。其主张是少训练、少专用启发式设计与跨 COP 接口通用性，并不意味着完全无领域建模。初始化、压缩、恢复和检查器仍然按问题类型设计。

对我们的启示：如果第二篇仅写“LLM 发现潜在改进位置、接收 solver 反馈、生成上下文相关决策”，与已有工作的重合会很大。真正需要明确的是 **什么证据支持改写哪种排序规律，以及如何把该规律沉淀为可复用程序**。

## 3. DRAGON 的完整算法链

**依据：§3、§3.1-3.3、Algorithm 1、Eq.1-5，PDF p.3-5（2811-2813）；Figure 2-3，PDF p.4（2812）。**

| 环节 | 输入与输出 | 有实质作用的条件 |
|---|---|---|
| 快速初始化 | 问题元数据 `M` -> 全局可行初解 `S0` | 为后续局部修复提供完整基准 |
| Decomposer `D` | `M, Si` -> 活动区域 `ai` 与静态区域 `si` | LLM 选择高潜力节点或物品，静态区域本轮保持 |
| Compress | `M, ai, si` -> `M'i, S'i, Ci` | 压缩时不能丢失静态区域对可行性和目标的影响 |
| Reconstructor `R` | `M'i, S'i, Ci` -> 局部候选解 | 在小数据中求解，并满足来自全局结构的额外约束 |
| 约束检查与记忆 | 候选解 -> 可行性、失败原因、后续提示 | 不可行尝试也保存，反馈不是只留成功样本 |
| 接受与整合 | 旧局部解、候选局部解 -> 全局更新 | 概率接受有时允许变差；恢复静态结构保持一致性 |
| 停止 | 时间与拒绝/无改进计数 | 限定搜索成本，具体口径应核实实现 |

### 3.1 分解 agent 与压缩的关键

分解 agent 不是先求解全局再抽取局部。它读当前元数据与解，输出一小组待优化节点/物品，由工程代码识别对应静态区域。活动部分小，重建 agent 才能利用 LLM 在小规模问题上的能力。

TSP/CVRP 中，静态连续路径可压缩为必须相邻的端点连接。重建时不能在该固定路径内部插入额外点；恢复时把压缩连接展开回原始路径。CVRP 还必须正确累计静态段内部需求，否则局部容量合法不等于全局合法。BPP/MKP 则通过已固定物品、剩余容量或静态集合的聚合表示携带约束。

这实际上已经认识到 **边界条件会影响局部重建**，所以我们不能把“首次考虑上下文/边界约束”作为贡献。我们应研究边界条件对 **同一对可行决策的完成价值排序** 的影响，并提供严格证据。

### 3.2 接受机制与“Improved solution”的实际含义

最小化时使用类似模拟退火的接受概率：

`P(accept) = min(1, exp(-(f(new)-f(old))/T))`。

因此被接受的当前状态不保证每次改善。Algorithm 1 返回当前解，其描述中的 improved 不能当成单调改善定理；若工程中需要“最终不比初解差”，应保留 best-so-far 并返回它。局部目标差与全局目标差一致也需要压缩/恢复正确且未更改的目标项相消。

论文伪码用连续拒绝计数 `r<N`；实验设置写连续 5 次无改进停止。拒绝与无改进不完全相同，尤其存在接受变差和等价解。复现时需要规定清楚，而不能只照标题理解停止条件。

### 3.3 可行性来源不是自然语言保证

§3.3 强调通过经验累积修正到满足约束，§4.1.4 明确存在问题专用 checker。结果中的可行性是外部检查与迭代修复共同实现的经验结果，主文没有给出“LLM 必然在有限步内找到可行解”的定理。

第二篇的固定 kernel 可以进一步把安全边界收紧：LLM 只生成优先级程序，合法候选、动作执行、可行性维护与最终完整解校验都由受测工程组件完成。这样能把程序质量与动作可行性分开，但仍需证明 kernel 的具体不变量，不能光靠命名。

## 4. 经验记忆、提示词与接口

**依据：§3.3、§4.1.4、Figure 2-3，PDF p.4-5（2812-2813）。**

DRAGON 的 memory 包含先前所有尝试，不限于可行解；不可行解附带违反的约束类型与原因。正样本让重建 agent 看见可行模式，负样本让它避开重复错误。图 3 的核心是候选、checker、失败注释、再生成，而不是额外训练模型权重。

主文没有详细证明长期记忆如何压缩、跨实例检索是否存在、截断规则如何影响效果。不能把该 memory 直接描述成已经学习出的通用知识库或已认证的 preference 数据集。

Figure 2 中的接口有几个可复用点：

- 元数据用 JSON，解用 XML/JSON，输出限定在可解析标签内。
- 分解输出是节点/物品 ID 列表，不要求 LLM 输出整套压缩逻辑。
- 重建输入包含目标、局部元数据、当前局部解、问题约束与固定片段要求。
- 失败反馈描述具体违约，而不是只报告一个目标数值。

附录 A 补充说明全部实验活动元素上限设为 20，并建议不要超过 50；固定路径可在允许条件下逆向。静态集合可聚合为大物品。这些是接口和表示选择，不是上下文优先级理论。[作者附录 A](https://arxiv.org/html/2601.06502v2#A1)

我们的证据 memory 应保留这些工程优点，但内容需要升级：每条记录应包含局部状态、两候选决策、两合法上下文、四个可行完成见证、条件目标定义、上下界来源、两条严格不等式、程序版本及验收状态。LLM 的解释应单独存放，不能混成 solver 证据。

## 5. LLM、预算与实验条件

Figure 7 的可完成模型平均 gap 为 `gpt-4o 19.06%`、`o3 15.64%`、`gpt-4.1 16.15%`。对应平均 API 调用约为 22.20、13.60、12.80；平均运行时间约为 2224.46 s、2871.49 s、355.61 s。`o3` 输出约 0.13M token，`gpt-4.1` 约 0.02M。这里仅是所选 TSPLIB 子集，不能推广为全部 COP 的模型结论。

`r1` 在超过 10k 节点的实例遇到作者记录的 65,536 输入 token 上限，图中灰色部分表示未完成，其成本和质量不能与完整组直接平均比较。作者因此认为 `gpt-4.1` 在其设置下质量、时延与 token 的平衡更实用。

对本项目的决策：**不需要使用“当前聊天模型的低阶复制版”**。离线合成器应是可替换 provider；本地 DeepSeek harness、OpenAI 兼容 API、离线 fixture 都接收同一证据包并输出同一受限程序规格。没有外部模型的演示可以检验流程，但 fixture 模式必须标明并不提供真实 LLM 合成证据。是否用小模型应由程序验收率、修复次数、总 token 与证据满足率决定，而非预先认定小模型更合适。

## 6. 实验结果究竟支持什么

**依据：§4.1-4.4、Table 1-3、Figure 4-8，PDF p.5-8（2813-2816）。**

### 6.1 数据与 oracle

- TSP：77 个 TSPLIB EUC_2D 实例，约 50 至 20k 节点，参照最优值或已知下界。
- CVRP：19 个 X/XML 实例，涵盖约 100 至 5k 节点；参照最优值或下界。
- BPP：Weibull-5k，参照 L2 下界。
- MKP：10 个合成实例，约 10-100 个 knapsack，容量均匀采样于 100-500，物品重量与价值采样于 1-100；oracle 使用 solver 最优值或上界。

MKP 的 knapsack 数范围沿用 §4.1.2 文字；Figure 8 又出现 `mkp_393_5` 等包含 5 个 knapsack 的命名，两处并不完全一致。真正复现时应以发布实例文件为准。

当 oracle 只是界时，所谓 optimality gap 是相对该界的差距，不能保证就是实际最优性差距。我们的证据表必须明确 `exact optimum`、`valid lower bound`、`valid upper bound`、`heuristic value`，不能都叫 oracle。

### 6.2 路由结果

TSP 总平均 gap：DRAGON 12.24%，ReEvo(a) 13.10%。DRAGON 在 500 节点以上分组优于该版本 ReEvo(a)，但最小规模组为 9.74%，ReEvo(a) 为 8.17%，并非全面胜出。大规模组仍有约 15%-19% gap，不能写成一般路由问题已接近最优。

CVRP 总平均 gap：DRAGON 20.15%，ReEvo(a) 24.17%。在 100-200 与 200-500 分组，DRAGON 分别为 25.56% 与 29.35%，反而较差；更大规模组优势更明显。文中叙述“all cases”的措辞不应掩盖 Table 1 的组别差异。

OPRO 超时、SGE 不可行、LMEA 高 gap、OR-Tools 超时都是 **作者实现与预算下的结果**。这不能推出 OR-Tools 或传统优化作为一个整体无法求解这些问题，也不能证明对最强专业 solver 的优势。

### 6.3 分解/重建 3×3 消融

Figure 6 经渲染核对，TSPLIB 子集 gap 如下：

| Decomposition | Heuristic reconstruction | Solver reconstruction | LLM reconstruction |
|---|---:|---:|---:|
| Random | 10.94 | 10.02 | 11.55 |
| Heuristic | 11.88 | 9.94 | 10.79 |
| LLM | 10.28 | **9.48** | 9.74 |

最强的是 **LLM×Solver**，不是 LLM×LLM。LLM×LLM 优于 Heuristic×Solver，但还不能由此说明 LLM reconstruction 本身比 solver 强。该消融支持“LLM 分解有潜力，solver 重建有质量优势，双 LLM 在建模便利性上有价值”，不支持“越多 LLM 越好”。

Table 2 的领域知识需求是作者的定性评价，没有测量实际工程人时；不能把 `(none, none)` 理解成无需编写任何问题专用代码。

### 6.4 Packing 与百万变量主张

BPP 表 3：DRAGON 对 L2 下界平均 gap 0.33%，FunSearch 0.69%，EoH 0.66%，EoH expert 0.55%，ReEvo(a) 3.46%。DRAGON 推理时间 487.873 s，FunSearch 2.292 s，ReEvo(a) 56.677 s；EoH 时间未提供。EoH 数据直接取自原论文，其发现启发式的离线成本没有进入该推理时间比较。

因此该结果支持质量优势与显著更高的在线开销并存。比较离线代码发现与在线直接求解时，应同时报告“发现成本、部署成本、实例数量”，才能评估摊销。

MKP 的约 3M 变量指物品数×knapsack 数的完整分配矩阵规模，**不是把 3M 变量同时装进一次 LLM 提示**。Figure 8 中大实例 DRAGON gap 仍低于 0.5%；首页摘要的 0.16% 是特定超大场景结果。不要把它写成所有四个任务都是 0.16%。

## 7. 局限与应公平保留的优点

**依据：§4.5、§5，PDF p.8（2816）；以下评价是阅读判断。**

作者自己承认分解策略和提示形式敏感，大上下文与多轮 API 导致较高开销，小实例效率不佳，并计划加入外部 solver、约束自动建模和协调 agent。我们无需把这些已承认局限包装成发现。

值得保留的优点：跨四类 COP 的统一状态接口、静态结构携带约束、失败归因的外部检查、可替换分解与重建器、同时记录质量和 token/时延、以完整可行初解保障迭代起点。

目前主文不足以证明：任意新约束都能无建模迁移，动态分布下必然优于离线代码发现，所有可行修复都能终止，或者相对最强专用算法具有普遍优势。重复次数、随机方差和显著性也不足以从主文确认，应查日志与附录而非补造。

## 8. 官方代码核验：可以借鉴结构，不能直接当稳定底座

这次只读核验了 [dragon.py](https://github.com/skychan/DARGON/blob/main/dragon.py) 与 [main.py](https://github.com/skychan/DARGON/blob/main/main.py)，没有执行作者代码、没有付费 API 调用。

`dragon.py` 包含压缩坐标重编号、静态段累计需求、剩余 knapsack 容量、恢复原始 ID、全局 checker、模拟退火接受、best-so-far 和逐轮 checkpoint。可以借鉴“压缩/恢复显式分开”和“保存解、对话、指标”的结构。

复现风险：当前 `solve` 以迭代循环和无改进计数运行；`main.py` 解析的 `--time_limit` 未传入求解器；默认 `repair_method=greedy` 又不在其允许的枚举中。说明启动配置与论文预算需要人工审计。我们应采用独立的、版本固定的参考配置，不能把作者当前仓库直接称为按论文预算开箱即跑的稳定框架。

## 9. 与最新摘要的逐项比较

本节“我们的设计”依据当前第二篇已明确的目标：同一对竞争决策在两种合法约束下都能完成，条件完成偏好严格反转；边界条件优化给出四个有效 L/U 证据；证据导出的成对要求驱动受限 context priority 程序合成；通过 disagreement acquisition 追加证据；部署时使用固定可行 kernel，无在线 LLM。

| 比较维度 | DRAGON 已有内容 | 第二篇应增加的明确内容 | 能否单独称为新颖贡献 |
|---|---|---|---|
| 上下文/边界 | 静态片段压缩，局部附加约束 | 研究边界改变时的同对决策完成偏好 | “考虑约束”不能；严格反转证据可能可以 |
| 反馈 | checker 违约注释与尝试 memory | solver 界、完成见证、条件目标定义的证据包 | “有反馈”不能；可复核的排序证书可能可以 |
| 对比 | 旧/新局部解目标改善 | 两合法上下文中的同一候选对，反向严格关系 | 比单次改善有更清楚的识别目标 |
| LLM 输出 | 活动元素与局部解 | 满足证据成对要求的受限优先级程序 | 代码生成本身已有先例，约束规格才是重点 |
| 查询 | 在线直接求解迭代 | 程序间分歧触发有针对性的补证 | 主动学习思想已有先例，应证明本任务收益 |
| 执行 | 每实例调用分解/重建 LLM | 冻结程序与固定 kernel，无在线 LLM | 与 DRAGON 差异明确，但离线合成已有先例 |
| 目标 | 大规模实例可行性、质量、通用性 | 学习可转移的上下文排序规律并审计来源 | 尚需同预算对照与迁移验证 |

不能写“DRAGON 只关注 feasibility，而我们第一次优化质量”：它显然优化质量。也不能写“DRAGON 没有上下文约束”“DRAGON 没有经验反馈”“我们的无在线 LLM 是首次”，这些都不成立。

## 10. 严格反转与四个证书：应写进实现的不变量

对最小化问题，定义固定局部状态 `s`、候选决策 `d∈{a,b}`、合法上下文 `c∈{c1,c2}` 下的条件最优完成值：

`V(d,c) = min { f(d,z;c) : z ∈ F(d,c) }`。

必须先保证四个组合 `F(a,c1), F(b,c1), F(a,c2), F(b,c2)` 全部非空。上下文只改变允许的边界/承诺条件；局部决策身份、目标单位、比较口径与目标定义保持一致。不要把 a 在 c1 不可行而 b 可行的情况称为优先级反转。

有效界满足 `L(d,c) <= V(d,c) <= U(d,c)`，其中 U 由一个被独立检查的可行完成解提供，L 来自精确证明或有效 relaxation。两条不等式：

`U(a,c1) < L(b,c1)`

`U(b,c2) < L(a,c2)`

即可证明 `V(a,c1) < V(b,c1)` 且 `V(b,c2) < V(a,c2)`。对应最小充分的四个定向证书是 `U(a,c1), L(b,c1), U(b,c2), L(a,c2)`。实现可以存四个 cell 的完整 `[L,U]` 区间，但不要混淆“四个组合”和“四个数”。

特别风险：这四个定向界 **本身不证明败者在对应上下文可行**，败者仍需单独的 completion witness；一个有限 lower bound 不等于存在可行解。LLM 评分、rollout 均值或 solver incumbent 不能充当最小化 lower bound。未分离区间只能标记 `unresolved`，不能按最好的观察值强制给出标签。

小规模 exact oracle 可用于验证数学链和复核器；大规模应提供可替换 solver/relaxation。初版 exact 枚举能跑通不意味着最终大实例求证预算已经解决。数值严格性应使用整数目标或可靠误差容限；固定 margin 不能被不一致的单位缩放制造出来。

如果 oracle 只优化了活动子问题，证书也只针对其实际定义的条件完成空间成立。必须写清静态方案是被上下文固定，还是剩余全局决策仍允许重新优化；不能把固定静态解的局部最优冒称原全局完成值的最优性证明。

这比 DRAGON 的单次局部修复更有针对性，但只认证了 **这些上下文和决策对** 的关系，不证明全局最优、所有状态正确或部署收益。

## 11. 邻近工作：最少但必要的定位

以下只用于防止重复包装，不是完整综述。

**HeurAgenix** 在演化阶段利用较差/较好解对比提炼改进策略，求解时按状态动态选择启发式，并允许 LLM 或轻量模型 selector。其官方代码也提供 rollout budget 等控制。因此“解对比反馈”“状态相关选择”“用小模型降低推理成本”都已有先例。我们的差异应是同一候选对的双上下文严格反转与可检查的完成界，而不是普通 contrastive 改进反馈。[作者论文](https://arxiv.org/abs/2506.15196)，[官方代码](https://github.com/microsoft/HeurAgenix)

**EoH** 用 LLM 与演化计算共同探索启发式思想和代码，以任务评价决定保留与演化。**FunSearch** 将 LLM 程序提案与系统 evaluator、程序数据库结合，搜索可部署函数。因此“离线 LLM 合成、在线只执行程序”不是独立新颖点。第二篇应把成对证据转成合成规格，保留未满足要求作为可复核反例，并比较普通标量适应度搜索与证据驱动搜索的差异。[EoH 原论文](https://proceedings.mlr.press/v235/liu24bs.html)，[FunSearch 原论文](https://www.nature.com/articles/s41586-023-06924-6)

ReEvo 同样已有反思反馈的启发式演化。第二篇的原论文定位不能只击败 DRAGON，还必须解释为何不是把一般演化程序搜索换了提示词。

## 12. 不降级创新性的工程路线

建议保留完整研究主张，同时把实现分层推进：

1. **证据层先正确。** 实例、局部状态、候选对、合法上下文、完成 oracle、界、证书验证器分开。第一个小例子必须满足四组合可行、两严格方向相反；不满足就明确拒绝。
2. **合成层输出受限程序。** 输入成对要求、合法可观察 context features 和验收说明；输出 AST/DSL/受限表达式。静态限制、有限性检查、成对要求回放与候选程序验证都完成后才能入 archive。无需执行 LLM 任意 Python。
3. **主动查询层保留选择依据。** 两个合格程序在同一状态下排序不同才构成具体 disagreement；该分歧不等于证据成立，需请求 oracle 并验证，失败/未决查询也记成本。
4. **部署层冻结。** kernel 负责候选可行性、动作合法性、后续完成和完整解校验；优先级程序只排序。禁止读 oracle 标签、证书真值、实例 ID 查表或调用外部模型来完成在线决策。
5. **实验层晚于底座。** 当前可以完成 smoke test 与数学链复核；效果实验再检验常规 scalar-search、无 context、普通 rollout 标签、随机 acquisition、无严格反转筛选等消融。

LLM 预算应记录离线调用数、实际/估计 token、候选程序数、被拒绝原因、证据求解时间、缓存命中和最终部署耗时。比较 DRAGON 时单实例在线预算和跨实例摊销预算都要报告，不能只把我们在线零调用与对方全部调用相比较。

## 13. 未来必须通过的创新性与有效性审查

- **边界识别力：** 在保持局部特征和可行性的条件下，上下文改变确实要求反向排序，普通 context-free priority 无法同时满足。给出形式化命题与可复核例子。
- **非查表泛化：** 程序只能看部署可得特征；在未见过的 context、规模、分布上满足新的已认证要求。训练证据与测试证据按问题/上下文族分开。
- **证据不可替代性：** 在相同 kernel、模型、合成预算与 solver 预算下，严格界证据优于 noisy rollout 或只看最终目标的反馈。
- **主动查询价值：** 同求证预算下 disagreement acquisition 带来更多有效反转或更好部署结果，不能只展示采到几个好案例。
- **相对近邻：** 与 EoH/FunSearch/ReEvo/HeurAgenix 风格的 baseline 对齐可用接口和成本；对 DRAGON 保持其在线求解路线的公平实现。

在这些审查完成前，可诚实主张“实现了一条比单次改进反馈更严格的上下文排序证据链，并构建了相应离线合成框架”；不能主张“已证明创新性比 AAMAS 2026 DRAGON 更高”或“已经全面优于现有方法”。当前任务不要求实际验证效果，但应把上述接口和证据审计能力留在底座中，防止后续因赶工将创新退化为普通 prompt 调参。
