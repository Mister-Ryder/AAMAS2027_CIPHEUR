# 真实 LLM 角色与合成成本（报告小节草稿）

本轮 LLM 参与发生在**离线算法设计阶段**：真实 Codex CLI 根据冻结的 TRAIN 决策关系、合法图操作库与训练反馈生成可执行的特征—评分规则程序。正式部署执行选定程序，从当前冲突图与当前可行动作集合重新计算结构特征，再由固定可行性内核构建和改进完整调度。部署没有在线 LLM 调用，也没有在线条件最优值证据查询。

## 为什么使用 LLM

核心困难不仅是调节评分公式，而是从结构证据中提出新的表示。已经认证的 TRAIN 案例中，两个动作在 E/J 两个约束配置下拥有完全相同的九维局部输入，严格偏好却反转，因此同一九维输入上的确定性点评分无法同时满足这两条要求。新增边出现在根动作一跳之外；已检查的一跳统计 T/Q 仍不变。这个证据说明必须考虑能到达缺失区别的表示，**并不说明 LLM 是唯一可能的合成器**。

LLM 在这里承担受限的程序提议器：将结构见证解释为可组合的图操作，提出小型特征表达式及相应规则，同时考虑完整图计算成本。所有候选均经过现有 `FeatureRuleProgram` 解析器和同一类型化图操作库验证。证书、程序合法性、可行性和最终收益仍由经典计算组件负责；LLM 自身的文字解释不构成证据。确定性 typed-grammar 搜索使用相同表达空间作为实质对照。能否证明 LLM 的增益，要由冻结的完整调度比较决定，不能由存在表示矛盾或更高 ranking fit 推导出来。

## 三个真实合成条件

| 条件 | 决策关系与完整 base9 输入表 | 认证表示矛盾及结构见证 | 可新增特征 |
|---|---|---|---|
| Witness-joint | 相同代表性 TRAIN 关系 | 有：条件上下界、图边、远处变边与路径 | 相同 typed 图操作库 |
| Relations-joint | 相同代表性 TRAIN 关系 | 无额外结构见证 | 相同 typed 图操作库 |
| Relations-rule-only | 相同代表性 TRAIN 关系 | 无额外结构见证 | 无，`features=[]` |

每个条件使用两组合成批次/重复请求，每批首轮八个候选，再允许一次训练反馈生成八个候选，最多32个候选。首轮b0/b1是分开的冷请求，第二轮两批次都收到同一条件汇总的16个首轮候选反馈，包含另一批次首轮表现，因此不是全程完全独立的统计合成重复。反馈另含相同经典基线数值参照；其他条件和grammar候选的源码、表现不进入该条件提示。所有失败和重复均消耗原候选名额，保留记录，不补槽、不静默重试。

比较控制的是**候选名额、合成轮数、语言、部署内核和优化时间预算**。Witness 输入结构证据较多，提示长度和 token 使用量会不同；本研究据实单列这些成本，不能把实验称为 token 预算相同。

## 数据边界与选择

合成只读取 `CP-AU/AP-r000/r001` 的已有冻结证据；全部 743 条严格关系用于评分符合率，提示只展示预定的 32 条代表性关系。条件证书描述既定 P/F/X 边界下的补完问题，并不宣称给出了完整 72 小时调度的全局最优值。完整调度候选评估使用四个 TRAIN 库与 A/W/E/J 配置的 16 张完整图，特征计算、输入加载、共享优化内核与最终验证计入同一预算。

在读取首轮完整调度成绩前，已固定 TRAIN 三目标短名单：完整调度逐图收益相对 degree 的均值、743 条严格关系符合率和实际 `meter.feature_work` 均值；Pareto 层内保留目标端点和确定性的 ordinal-rank 代表。随后仅在短名单中，以 r006 的 8 张图、2/10 秒和 seed 2 的 16 个配对项选择最终程序。TEST r008/r009 只在程序和协议冻结后评估，未进入提示、训练反馈或选择。可行的超时或程序报错后守护回退结果保留真实收益与状态；缺失或不可行结果不能通过删分母提高成绩。

## 实际调用与成本记录

请求的模型标签为 `gpt-6.1-sol`，推理配置为 `ultra`。CLI 在独立空目录下以只读模式执行，提示通过 stdin 输入；真实事件日志没有工具活动才接收输出。这里根据日志记录实际可观察的模型元数据；目前首轮日志没有报告 served 版本，故记录为 `unknown`，不把请求标签写成实际服务版本。

模型自述不能用于推断served版本。TEST统计以r008/r009两个独立场景组为单位，LLM批次可以分列，但不作为新的独立n。

首轮六次真实调用生成并验证了 48/48 个候选，工具调用数为 0。日志报告 input 112,192 tokens、output 49,705 tokens，其中 reasoning output 为 39,795 tokens；缓存读入和写入字段均为 0。Reasoning 已包含在 output 中，不能再次加进总量。Input + output 共 161,897 tokens。六调用的并发区间约 369.8 秒；逐调用耗时之和约 1,844.8 秒，二者含义不同。

两轮现已实际完成 12 次调用，96/96 个候选通过类型、语法和调用隔离检查，未发现真实工具活动。完整日志累计 input 395,828 tokens、output 108,914 tokens，其中 reasoning output 87,872 tokens；input + output 为 504,742 tokens，缓存读/写字段均为 0。所有调用的 served 版本仍未知。`generation_cost_all12.json` 顶层明确记为 `offline_LLM_calls_actual=12`；`index_generation_model_calls=0` 仅表示整理该索引的脚本没有再调用模型。首轮索引保留原样，其中旧 `model_calls=0` 也仅指索引脚本，不代表首轮真实生成次数。

全部 12 次调用逐次耗时之和约 4,027.8 秒。从第一轮最早开始到第二轮最后结束的区间约 2,174.8 秒，包含两轮之间的训练与反馈等待，不能当成 LLM 的净执行耗时。新增 48 个第二轮候选已逐个评估全部 743 条关系，没有重评首轮或 grammar 候选；零算术报错。第二轮并未提高各条件最高 ranking fit，不能把反馈环节本身描述为已证明的有效改进。

| 条件（两轮、两批次） | 真实调用 | input | output | reasoning（已含在output） | 逐调用wall之和（秒） |
|---|---:|---:|---:|---:|---:|
| Witness-joint | 4 | 160,420 | 41,588 | 31,470 | 1,532.313 |
| Relations-joint | 4 | 119,364 | 42,638 | 35,216 | 1,569.827 |
| Relations-rule-only | 4 | 116,044 | 24,688 | 21,186 | 925.625 |

每条件候选名额均为32，但实际token/时间不同，尤其结构见证输入更长，因此不能声称三条件合成费用完全相同。

`scripts/generation_cost_index.py` 从原始 CLI 事件、调用回执与 v2 接收报告生成每次及每条件成本索引，保存输入/输出/缓存/推理字段、耗时、有效候选数、已消耗名额、实际工具活动、未知模型身份和证据哈希。未提供计费回执或验证后的费率，因此不猜测货币成本。离线证据生成、评分符合率计算和完整 TRAIN/VAL 调度成本由各自回执另行报告。

这段说明只阐述机制与实验设计，尚不能作为 LLM 性能优越的结论。首轮确定性 grammar 候选的最高关系符合率超过 Witness 候选，这一事实应保留；最终结论需要同时呈现完整调度质量、计算成本、条件差异和负结果。

## VALIDATION后已冻结的实际程序

两轮共96个LLM候选与32个grammar候选都有完整743条TRAIN拟合及16张TRAIN图的调度/成本记录。预定规则形成七个池各四个候选，共28个程序；560次VALIDATION运行后冻结六个LLM程序和一个grammar程序，再加入预指定旧程序，文件为 `banks/frozen_final8.json`、`selection/final_program_ids.json`、`protocol.frozen.json`。没有第三轮生成，未根据TEST采用或修改程序。

最终七个新选定程序都为 `features=[]`。TRAIN的完整base9仍保留两个相反偏好对/两组循环SCC，故本轮选择**没有实现新增表示修复**。存在真实LLM生成和合法执行，也存在严格的信息瓶颈证据，但这两者不能代替“生成的新特征缓解瓶颈并改善完整调度”的证据。第八个旧冻结头含有以前的结构特征，属于旧控制，不能计入本轮LLM表示贡献。完整调度优劣须由冻结后比较给出；此处不读TEST或预写胜率。

所有真实响应的schema、响应内容和接收过程分别保存在 `llm_calls/<call_id>/response_schema.json`、`response.json`、`validated_bank.v2.json`，事件和回执SHA绑定原始生成。运行文档、成本报告和autoresearch日志用于专家审阅，不属于论文正文。
